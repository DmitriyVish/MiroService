# Логика оценки ответов кандидатов.
Оценка ответов кандидата устроена как конвейер: загрузили данные → привели тексты к единому виду → посчитали близость к эталону → (если есть критерии) добавили баллы за критерии → скорректировали за длину → применили “штрафы за качество ответа” → сохранили детальный отчёт в JSON.

## 1) Какие данные использовались
Код читает три JSON-файла:

- **Ответы кандидата** (`candidate_answers_v3.json`): текст по каждому вопросу.
- **HR-эталон** (`etalon_hr_results.json`): для каждого вопроса список критериев с весами/максимумами (используется как рубрика).
- **AI-эталон** (`etalon_ai_answers_struct.json`): структурированный эталонный ответ, который превращается в «обычный текст» для сравнения.

## 2) Шаг нормализации текста
Перед сравнением тексты приводятся к одинаковому формату:
- приводятся к нижнему регистру,
- убираются лишние пробелы,
- текст становится более “сравнимым” (чтобы косметические различия меньше влияли на метрику).

Это снижает шум: например, разный регистр или лишние пробелы не должны менять оценку.

## 3) Базовая оценка: семантическая близость к AI-эталону
Для каждого вопроса считается **cosine similarity** между ответом кандидата и AI-эталоном (через эмбеддинги).

Дальше cosine (0…1) переводится в шкалу **1…10** линейным маппингом с отсечками:
- всё ниже `COSINE_LO` прижимается к низу шкалы,
- всё выше `COSINE_HI` — к верху,
- промежуток интерполируется линейно.

Итог: получается базовый `cosine_1_10` — «насколько смысл ответа близок эталону».

## 4) Дополнительная оценка по HR-критериям (если есть)
Если в HR-эталоне для вопроса есть рубрика (критерии), код:
- для каждого критерия считает его “попадание” (простая проверка наличия/соответствия по ключевым признакам),
- суммирует баллы,
- нормирует итог к шкале **1…10**.

Так формируется `criteria_1_10` — «насколько ответ покрывает ожидаемые пункты HR-рубрики».

Если критериев нет, этот шаг пропускается.

## 5) Смешивание: единый балл до корректировок
Затем строится **смешанный балл**:
- если `criteria_1_10` существует:  
  `final_blend = 0.7 * cosine_1_10 + 0.3 * criteria_1_10`
- если критериев нет:  
  `final_blend = cosine_1_10`

Весами управляют константы `W_COSINE` и `W_CRITERIA`, но идея одна: основа — семантическая близость, а критерии добавляют структурную проверку «по рубрике».

## 6) Коррекция за длину относительно AI-эталона
Дальше применяется корректировка за длину ответа кандидата **по сравнению с длиной AI-эталона**:
- считается отношение длины `len(candidate) / len(ai_etalon)`,
- если ответ слишком короткий (ниже порога `LEN_TARGET_MIN_RATIO`) — добавляется штраф,
- если ответ умеренно длиннее — возможен небольшой бонус,
- изменения ограничены рамками `MAX_LEN_PENALTY` и `MAX_LEN_BONUS`,
- сглаживание регулируется `LEN_SMOOTHING`, чтобы не было резких скачков.

Это защищает от ситуаций, когда кандидат пишет слишком мало (смысл может “попасть” частично, но ответ объективно неполный).

## 7) Штрафы за “качество формулировки” (поверх всего)
После длины применяются штрафы “только вниз”, например:
- **неуверенность** (много “возможно”, “наверное”, “не знаю”),
- **неконкретика** (общие слова без деталей, действий, примеров).

Эти штрафы не могут повысить оценку — только снижают, если ответ выглядит слабым по стилю/содержательности.

## 8) Итог и отчёт по каждому вопросу
Для каждого вопроса в `results` сохраняются:
- исходные тексты (кандидат и эталон),
- `cosine` и `cosine_1_10`,
- (если было) `criteria_1_10` и детали по критериям,
- поправка за длину (`delta_score`),
- применённые штрафы,
- финальный балл.

В конце всё сохраняется в `candidate_evaluation_output.json`, чтобы можно было:
- объяснить итоговую оценку,
- отладить пороги/веса,
- увидеть, где именно ответ “просел” (близость, критерии, длина, штрафы).

# Описание кода для презентации (доклада)
Цель системы
Автоматизированная оценка ответов кандидатов на технические вопросы (например, для позиции Data Engineer). Оценка сочетает:

семантическое сходство с эталонными ответами (через embeddings);

соответствие ключевым критериям (наличие терминов, структур, логических элементов);

дополнительные штрафы/бонусы (длина ответа, неуверенность, конкретность).

1. Основные компоненты
1.1. Конфигурационные параметры

Пути к файлам:

CANDIDATE_FILE — ответы кандидата.

ETALON_HR_FILE — «человеческий» эталон (экспертная оценка).

ETALON_AI_FILE — AI-эталон (сгенерированный ответ).

Пороги для косинусного сходства: COSINE_LO (0.45), COSINE_HI (0.90).

Веса в итоговой оценке: W_COSINE (0.7), W_CRITERIA (0.3).

Настройки для корректировки по длине ответа (LEN_TARGET_MIN_RATIO, MAX_LEN_PENALTY и др.).

1.2. Справочные данные

UNCERTAINTY_PATTERNS — регулярные выражения для поиска маркеров неуверенности («не уверен», «возможно» и т.п.).

CONCRETENESS_CATEGORIES — категории терминов (ключи, ограничения, индексы и др.) для оценки конкретности ответа.

2. Вспомогательные функции
2.1. Работа с данными

load_json(), save_json() — загрузка/сохранение JSON-файлов.

preprocess_text() — очистка и нормализация текста (нижний регистр, удаление пунктуации).

normalize_question_id() — извлечение номера вопроса из ключа (например, «Вопрос 1» → «1»).

2.2. Оценка сходства

cosine_sim() — вычисление косинусного сходства между векторами.

cosine_to_score_linear() — преобразование сходства в балл от 1 до 10 с линейной нормализацией.

2.3. Анализ содержания

count_pattern_hits() — подсчёт совпадений с шаблонами (например, маркеры неуверенности).

concreteness_coverage() — оценка охвата тематических категорий (ключи, индексы и т.п.).

length_adjustment_by_ai_etalon() — корректировка балла за длину ответа относительно AI-эталона.

2.4. Формирование отчёта

generate_comment() — генерация текстового комментария по баллу.

ai_etalon_to_text() — преобразование AI-эталона в строку для сравнения.

3. Основная логика (evaluate())
3.1. Загрузка данных

Чтение JSON-файлов кандидата, HR- и AI-эталонов.

Нормализация ключей (извлечение номеров вопросов).

3.2. Векторизация текстов

Использование модели SentenceTransformer («all-MiniLM-L6-v2») для получения embeddings.

Вычисление косинусного сходства ответов кандидата с HR- и AI-эталонами.

3.3. Оценка по критериям

Для каждого вопроса:

Извлечение критериев через get_criteria_for_question().

Анализ ответа на наличие ключевых терминов (evaluate_criteria()).

Расчёт балла по критериям (criteria_score_1_10()).

3.4. Расчёт итогового балла

Балл по сходству (cosine_1_10) — линейная нормализация косинусного сходства.

Балл по критериям (criteria_1_10) — доля выполненных критериев (от 1 до 10).

Комбинированный балл — взвешенная сумма: 0.7 * cosine_1_10 + 0.3 * criteria_1_10.

Корректировки:

Штраф за неуверенность (apply_quality_adjustments_penalties_only()).

Бонус/штраф за длину ответа (length_adjustment_by_ai_etalon()).

Финальный балл — округлённое значение после всех корректировок.

3.5. Формирование отчёта

Сохранение результатов в JSON-файл (OUTPUT_FILE).

Включение:

исходных данных;

промежуточных баллов (сходство, критерии, корректировки);

комментариев;

предупреждений (например, отсутствующие ответы).

4. Оценка критериев (eval_criterias.py)
4.1. Структура критериев
Для каждого вопроса задан список критериев (например, для «Вопрос 1»: «Дополнительные поля», «Первичный/внешний ключи» и др.). Каждый критерий содержит:

name — название.

keywords — список ключевых слов/фраз для поиска.

inverted (опционально) — инвертированный критерий (например, «отсутствие ошибок»).

4.2. Логика проверки

Нормализация текста — приведение к нижнему регистру, удаление лишних пробелов.

Поиск совпадений — проверка наличия ключевых слов (с учётом границ слов для отдельных терминов).

Расчёт балла — доля выполненных критериев, нормированная в диапазон 1–10.

4.3. Примеры критериев

«Первичный/внешний ключи» — поиск упоминаний primary key, foreign key, client_id и т.п.

«Нормализация» — проверка на термины 3nf, отдельная таблица, справочник.

«HAVING» — контроль использования агрегатных функций в SQL-запросах.

5. Итоговый результат
Выходной JSON содержит:

input — пути к исходным файлам.

scoring — параметры оценки (веса, пороги, формулы).

warnings — предупреждения (например, отсутствующие ответы).

results — детальные результаты по каждому вопросу:

ответ кандидата;

баллы по сходству и критериям;

корректировки;

финальный балл и комментарий.

Пример вывода:

json
{
  "Номер вопроса": "1",
  "Ответ кандидата": "Нужно добавить поле birth_date...",
  "Cosine HR": 0.85,
  "Criteria (1..10)": 8.2,
  "Оценка (final)": 8.5,
  "Комментарий": "Ответ полностью соответствует эталону..."
}
6. Ключевые преимущества
Комплексный анализ — сочетание семантики (embeddings) и экспертных критериев.

Гибкость — легко добавлять новые вопросы и критерии.

Прозрачность — детальный отчёт с объяснением баллов.

Автоматизация — минимизация ручного труда при оценке массовых ответов.
